# v0.7 prototype notes

## Confirmed map-space transform

The known remaining Veithurgard Raven is:

```text
world = (-64.850898742676, 12.987384796143, 787.30694580078)
map   = (3.2117712497711, 0.8695997595787)
```

The v0.6.x tests established that the map icon root created by `Map.CreateMarkerIcon()` is effectively tied to the backing native marker position, but the `untracked` child of a discovered `RadiusType` icon accepts a deferred `SetLocalPosition()` offset. Re-applying that offset for the first UI frames places the child at the arbitrary Raven map coordinate.

## v0.6.4

- Direct `Camera.PointAt(mapVector, true)` correctly centres the map on the solved Raven coordinate.
- Repeated deferred child transforms keep the separate visual at the Raven coordinate.
- `Camera.PointAtGO(child)` is not suitable because it resolves the backing marker root rather than the moved child.

## v0.6.5 / v0.6.5.1

- Native marker `Coordinates` can be assigned syntactically from Lua but the change is not live.
- Re-reading the marker returns the original world coordinates.
- Therefore an existing native marker cannot be turned into an arbitrary world-space compass target by mutating its coordinate field.

## v0.7

- Map Add/Remove-to-Compass interaction can toggle a shared arbitrary Raven XYZ target.
- The first HUD update attempt was shadowed by `MainHUD:Setup()` assigning its own instance `Update` function in non-gold builds.
- The moved RadiusType child did not behave like a complete stock marker for cursor snap/selection.

## v0.7.1

- Wrapping the final instance `self.Update` inside `MainHUD:Setup()` fixes the custom HUD update hook.
- A discovered DockPoint works as a native interaction proxy, but using it only repurposes the existing old/high-water dock. It does not create a new marker at the Raven location, so this architecture was rejected.
- `Compass_Radius:GetLocalPosition()` is unavailable, causing the first HUD rendering attempt to fail.

## v0.7.2 user result

Map:

- Separate custom child lands correctly at the Raven coordinate:

```text
x=3.2117714881897
z=0.86959981918335
```

- The moved child can enter the map collision table (`CUSTOM_COLLISION hit=true`).
- The first Add to Compass action succeeds and activates the arbitrary Raven XYZ.
- The visual still looks like a quest/Omega marker despite a child-level `DockPoint` material swap.
- On subsequent map opens the fallback selection is cleared by the map's automatic initial non-custom collision, causing Add/Remove to disappear.
- No satisfactory native auto-snap was observed.

HUD:

- The final instance update hook works.
- World-space reads/writes work on the compass UI object.
- Bearing and distance update correctly as the player moves and rotates.
- `Compass_Radius` is the complete gold radius/accent strip, not an individual target marker. Moving it produces a doubled gold compass, so that visual path is rejected.

## v0.7.3 direction

The v0.7.3 test build changes the prototype as follows:

1. Prefer a discovered `RadiusType` template with no quest association before falling back to any RadiusType.
2. Try `DockPoint` material swap on both the duplicate icon root and moved child.
3. Preserve Raven fallback selection through the automatic initial terrain collision after map reopen, then clear normally after a short grace period.
4. When the moved child enters the collision table, call `Camera.PointAt(targetMapPosition, true)` as a custom snap/recentre experiment.
5. Stop moving `Compass_Radius` entirely so the stock compass remains visually intact.
6. Continue computing arbitrary Raven bearing without drawing it.
7. Dump the `Compass`, `Compass_Base`, and `Compass_Radius` child hierarchy once so a later build can identify a genuine small marker/icon GO for the custom HUD indicator.

## Safety

All prototypes in this line remain read-only with respect to progression:

- no `Map.ChangeMarkerState()`
- no quest-state mutation
- no collectible-state mutation
- no synthetic save writes
- no hidden marker IDs rendered
